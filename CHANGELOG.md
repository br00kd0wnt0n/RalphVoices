- **Studio: carousel cards, and the Meta headline as post copy.** Item E of live versions (Brook, 30 Sep); no migration.
  - **Card sequences.** On a CAROUSEL territory with on-image text ticked, Write & brief asks for card sequences instead of loose lines: 3 sequences × 4 cards by default (up to 6 × 10). A sequence is one idea: card 1 is the hook, the middle cards build it, the last card pays it off. Each card is written against its own visible limit. Each card is stored as a line with `card` and `sequence_id`. Review shows "card 2 of 4 · sequence S1" and has **Keep the whole sequence**, as well as keeping card by card. The estimate prices the sequences.
  - **Ready: cards per visual.** A carousel visual has card slots (4 by default, up to 10), shared by every version on the visual. Each card can be swapped for another line, cards can be reordered, and a whole sequence can be applied at once. The sign-off stores each card with its number (`on_image[].card`).
  - **Pre-flight: card by card.** Card k's text must be on card k: matched on its card, amber `COPY_CARD_ORDER` when found on another card ("On card 3, expected card 2"), amber when reworded, red `COPY_CARD_MISSING` when not on the asset. The end-card disclaimer check is unchanged.
  - **Version checks across cards.** Each card counts as a field of the ad (`meta_on_image#2`). So card 2 restating card 1 is a repeat, the conflicts check sees the end card against the hook, and a claim on one card with its caveat only on another is red.
  - **Handoff.** A carousel visual lists its cards in order (MD), and the CSV and compliance sheet have a column per card, repeated on every code of the visual.
  - **Meta headline is post copy.** Text on the image is its own field now, so Pre-flight no longer looks for the headline on the image (`POST_COPY_FIELDS`; copyMatch's headline is `onAsset: 'no'`). A caveat that belongs with a claim is checked inside the ad at Ready (version check "split claims").

- **B3 weekly read (VOICES v2; migration 016).** `backend/scripts/weekly.ts` ingests Meta and TikTok ad-level exports into `live_ingests`, `live_ads` and `live_metrics`, and drafts the weekly note.
  - **Ingest:** names are parsed by `PERSONA_TERRITORY_FORMAT_v#_PLATFORM_YYMMDD`, tolerating case, spaces, Studio's long format names and suffixes. Bad names are quarantined with a reason and listed, never dropped. Creative reads use prospecting ads only (a configurable rule on campaign or ad set name). Features join from a Studio shortlist or B2 audit by naming stub. Re-ingesting a file is idempotent.
  - **Model** (`backend/src/services/weekly/`, pure): beta-binomial rates (hook rate, link CTR, quotes per 1,000) shrunk towards persona × platform × format means; seeded Monte Carlo P(best in ad set); scale, cut or keep testing against thresholds written down in `backend/config/weekly-read.json` before any data; feature and format effects from one weighted regression, with 90% ranges and "not enough data".
  - **Note and ledger:** a Markdown note per persona (what moved, how sure we are, three actions) plus a CSV ledger. Every estimate carries its range, and a wording check bans "predict", "winner" and scores. Optional GPT-4o prose is rejected if it adds a number.
  - **Hold bars (config v2):** a call made last week stays until the evidence falls well back (scale while P(best) ≥ 0.6, cut while P(worse than median) ≥ 0.75), so ads near a threshold don't flip week to week. Reads are chained week by week from the start of the flight (`series.ts`).
  - **Config v3 (review fixes approved by Brook):** ties and calls come from the same draws (tied = fewer than 9 in 10 put one ad ahead), so no ad is scaled or cut against an ad it's tied with. No scale or cut in an ad set with fewer than 3 readable ads. The note opens with one plain-English screen (headline and at most 3 actions per persona, plus one account line), followed by an appendix. `--audience client` gives the front only, with readable ad labels, stub in plain brackets (territory names read at runtime from Studio's rules). Cost per enrollment is hidden below 5 enrollments.
  - **Stored reads:** `live_reads` (in 016) keeps each week's per-ad result, and the view `live_latest_reads` gives the latest per naming stub for the planned Studio Live tab (`latestReads()`, `weekly.ts latest`).
  - **Naming v5:** ad names may carry a visual letter, copy line and region (`FAM_SUMMER_ST_A2_US_META_261013`); the older `_v#_` form is still accepted. The forms live in `naming.forms` in the config. Region is stored on `live_ads` and `live_reads`, joins the cell (persona × platform × region) and the feature strata, and shows in labels ("static A2 (US, Meta)").
  - **Conversions confirmed (config v6, Add3 29 Sep):** Meta's "Checkouts initiated" is read as quotes and "Purchases" as enrollments. TikTok's "Purchases (website)" is mapped to enrollments as an assumption. The attribution window is still open.

- **Studio: live versions (one code = one ad), on-image text per visual, version checks.** Brook and Nick, 30 Sep; no migration (sign-off JSONB).
  - **Versions.** A naming code is now one ad: a version is a set of fields. On Meta that's primary text + headline (description optional); on TikTok, caption (hook optional). The lead builds versions at Ready for production per visual letter, three per visual by default. A line can be in several versions (one headline in A1 and A2). The `<line>` digit of the code is now the version number; the format is unchanged. A version with the same lines as in the last sign-off keeps its code. An incomplete version is refused, with what it needs ("needs headline"). Field roles come from the rules' `in_version` (`required` / `optional` / `per_visual`), with defaults.
  - **What the sign-off stores.** Per version: its code, visual, lines, fields and a per-field hash (`signoff.versions`). Per visual: the on-image text (`signoff.on_image`). The expectation names codes.
  - **Codes downstream.** Pre-flight, compliance (now recorded per code: `line.compliance_by_code`), the handoff CSV/MD (one row per code, a column per field), the compliance sheet and the B3 features all work per code. Sign-offs from before versions (one code per line) are still read.
  - **On-image text** (`meta_on_image`) belongs to the visual: one per visual letter, no code of its own. It's added to the copy of every code on the visual (Pre-flight copy match: must be on the asset), shown once per asset at Compliance, and repeated on each code's row in the handoff.
  - **Version checks at Ready** inform and never block. Each flag has a rule id and a source.
    - Repeats between the fields of one ad (amber, word overlap, quoted).
    - Two versions on one visual too alike (amber).
    - Fields that contradict, undercut or clash in tone (amber; one model call per version, stage `version-check`, priced before it runs, about $0.001 per version; kept per wording, so an unchanged version isn't paid for twice).
    - A compliance claim in one field with its caveat only in another, or nowhere (red; the rules' `require` items).
    Thresholds are in `services/studio/versionChecks.json`. Checks are stored in the sign-off.
  - **Shortlist** is grouped by field, with the codes a line was signed off in.
  - **Leftover spend reservations** older than 2 hours are cleared on startup, each one logged.

  Tests: `studioVersionChecks.test.ts` (checks 1–4, TikTok, incomplete versions), a live-versions end-to-end test in `studioPg.test.ts` (A1–A3 sharing a headline plus on-image A, through sign-off, Pre-flight, per-code compliance and handoff), stale reservations (`studioBudget.test.ts`, `studioPg.test.ts`), and the Ready and concurrency tests reworked to versions. - **Studio: two people at once.** From a local two-user test (30 Sep); no migration.
  - **Per-run lock.** Every change to a run (decisions, overrides, compliance, re-checks, added lines, checker saves, sheet imports) happens under a per-run lock (`StudioStore.withLock`: Postgres advisory locks in one transaction; an in-process lock for the file store), on fresh data. Decisions, compliance statuses and edits are no longer lost to last-write-wins, and history entries chain.
  - **Added lines.** New lines get their ids under the lock, so two people adding to one run never collide. A person's added line records who added it (`added_by`, and a history row).

If someone else signed the set off since the screen loaded, it gives a clear 409 ("X just signed this set off: reload"). Lines a later set leaves out are marked (`ready.superseded_by`) and keep their codes. Only the creative lead or an admin can sign off (`STUDIO_READY_EMAILS`).

  - **Spend cap.** The cap reserves each run's estimate up front, so runs started together can't pass it.

  - **Compliance note.** The Compliance step shows why each copy override was made.

For rules v2.10's `meta_on_image`: the writer is told it's text on the image that goes with the visual (the rules can override this with `writer_note`), the audit's lead fields and copy checks include it, and it's matched on the asset as "must".

  - **Panels are generated in chunks of 10** (`utils/variantChunks.ts`), with shortfalls requested again and duplicate first names dropped. A single call asked for 30 had returned 11. If a panel still comes up short, `POST /personas/:id/variants` returns 502 with `requested_count`/`generated_count` and leaves the existing panel untouched (it used to save the short panel). This applies to every panel build.
  - **Feed realism** (`variant_config.realism: true`, "Feed realism" checkbox): the response prompt anchors the scale (5 = a typical ad you'd scroll past), gives the panel member its category baseline from `brand_context` (which the response prompt never saw before), and turns `attitude_score` into behaviour ("you stop for fewer than 1 in 20 of these ads"). `utils/realism.ts`.
  - **Voice samples that don't pitch**: `voice_style: 'lived'` on `PUT /personas/:id` (with `regenerate_voice`) or `{style: 'lived'}` on `POST /personas/:id/voice` writes the sample about the pet, household and money, never the product category. `PUT /personas/:id` also accepts a hand-written `voice_sample`. The default prompt had written pro-insurance monologues that sat in every response prompt.
  - **Intent probes** (`variant_config.probes: true`, "Intent probes" checkbox): after the in-character answer, three one-word follow-ups (stop / tap / take the next step), scored as P(Yes) from token logprobs. Stored in `test_responses.probes` (migration 008), averaged into `summary.probes`, and per persona in `segments.by_persona[...].probes`. A failed probe is null and never drops the panel member. About four times the OpenAI calls per panel member. `utils/probes.ts`.
  - `segments.by_persona` now also carries a per-persona `ralph_score` (v1 maths), shown on the By Persona card with probe percentages.
  - `GET /tests/:id/responses` returns `persona_id` on each response.
  - Tests: `backend/tests/twinFixes.test.ts`.
  - Migration numbering: 008 is `response_probes`; the build plan's `persona_evidence` takes the next free number.

- **Retries no longer stack.** The concept-response OpenAI call now passes `maxRetries: 0`, so `withRetry` (`backend/src/utils/retry.ts`) is the only retry layer: 3 attempts per panel member instead of 9. `withRetry` now also retries 408/409 and honours `Retry-After`, which the SDK previously handled. Tests: `backend/tests/retry.test.ts`.
- **Unparseable concept responses are no longer scored 5/5/5/5.** `generateConceptResponse` now throws `ScoreParseError` when it can't read the four scores (`backend/src/utils/parseConceptResponse.ts`). `withRetry` retries it, and a panel member that still fails is recorded in `options.dropouts`. The parser is also more tolerant: ```json fences, trailing prose, numeric strings and a missing `---SCORES---` line with the object still present all parse now. Before, most of these silently became 5s. This changes how existing concept tests run and is not behind a flag. Tests: `backend/tests/parseConceptResponse.test.ts`.
- **RalphScore computed server-side.** `backend/src/utils/ralphScore.ts` (same maths as the old client function) runs when results are written; `test_results.summary` now stores `ralph_score` and `ralph_score_version: 1`. The results page and test comparison read the stored value and fall back to `frontend/src/lib/ralphScore.ts` (an identical mirror) for older tests. Fixture test `backend/tests/ralphScore.test.ts` (`cd backend && npm test`) proves backend and frontend agree and match the pre-move formula. Backfill: `backend/scripts/backfill-ralph-score.ts` (`--dry-run`; refuses non-local hosts without `--allow-remote`).
- Test comparison card now shows the compared test's real RalphScore. It used a rougher inline formula (sentiment rounded first) that could disagree with that test's own results page by a point.
- `segments.by_persona` added to results (keyed by persona name, with `persona_id`; count, avg sentiment, avg engagement) and shown as a "By Persona" card on the results Dashboard tab.
- `options.image_detail` (`low` default, `high`, `auto`) on `POST /tests`, passed to the vision `image_url.detail`. "High-detail images" checkbox on the concept-first configure step. Default behaviour is unchanged (`low`).
- Concept-first: selected personas with no panel are no longer silently skipped. Their panels are built on Run (`variants_per_persona` members, Meta + TikTok), with per-persona progress; if a build fails, the run is blocked with a message and no test is created. `POST /tests/:id/run` also returns `personas_without_panel` and logs a warning for API callers.
- Default platforms for new panels are now Facebook, Instagram and TikTok (`DEFAULT_PLATFORMS` in both constants files), replacing TikTok/Instagram/YouTube/Twitter-X. Existing personas and panels are untouched.
- Dropouts recorded: panel members that still fail after retries are stored in `tests.options.dropouts` (`{count, variant_ids}`). The results page shows "n of N panel members responded" when some didn't.
- Edit & Retry now restores the "Calibration constraints" and "High-detail images" settings from the original test.

- **Panel freeze (migration 007).** Regenerating a persona's variants no longer deletes test history. Before, `POST /personas/:id/variants` deleted every variant and `test_responses` cascaded with them. Now the new panel is generated first; variants never used in a test are deleted; used ones are soft-retired (`retired_at`) and their responses kept. Each regeneration bumps `panel_version` (returned in the response). The panel swap runs in one transaction, and a failed generation leaves the existing panel untouched. Test runs, persona lists, variant lists and project persona-copy only see active variants.
- Per-test `variant_config.vector_constraints` (default on). `false` skips vector disposition constraints and anchor seeding for that test, so pre-test sweeps of closely related concepts don't pull each other's scores together. Exposed as a "Calibration constraints" checkbox on the concept-first configure step.
